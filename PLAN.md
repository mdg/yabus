yabus: Bus Route Drawing App
============================

A web app for drawing numbered bus routes on a map. Initial target area: **Hudson County,
NJ** and its neighbors, which have many one-way streets.

Goals
-----

-   Display an interactive map of the target area.
-   Let the user create a route by clicking to place waypoints on the map.
-   Give each route a number, a name and a color.
-   Snap routes to roads using bus-appropriate routing that respects one-way streets.
-   Render routes with the route number labeled along the line and arrows showing
    direction of travel.
-   Provide three views: edit, read-only single route, and a composite of all of one
    user's routes.
-   Keep a user's routes in `localStorage` and replicate them to one GeoJSON file per
    route on the server's filesystem.

Non-goals for this plan
-----------------------

Items marked "later" are collected in "Deferred to later plans" at the bottom.

-   Login and accounts (later). The username is hardcoded, and session IDs are generated by
    the server.
-   Import/export of GeoJSON files (later).
-   Route selection / filtering in the composite view (later).
-   Freehand line drawing. Routes are only built from clicked waypoints. Not planned at
    all.
-   Schedules, timetables, or real transit feeds (GTFS).
-   Trip planning or rider-facing features.

Route model
-----------

A route is a **loop** or **point-to-point**. Every route has either one or two *paths*,
where each path is a single line of travel in one direction.

  -----------------------------------------------------------------------------------------
  Kind                          Paths                         Description
  ----------------------------- ----------------------------- -----------------------------
  **Loop**                      1                             Start and end are the same
                                                              point. Always exactly one
                                                              path.

  **Point-to-point, one         1                             Runs from endpoint A to
  direction**                                                 endpoint B only. This is the
                                                              common case and the default.

  **Point-to-point,             2                             Path 0 runs A to B. Path 1 is
  bidirectional**                                             the return trip, B to A, and
                                                              may follow different streets.
  -----------------------------------------------------------------------------------------

Rules:

-   A route has **at most 2 endpoints**: A and B for point-to-point, or a single shared
    start/end point for a loop.
-   A bidirectional route **always uses the same two endpoints** for both paths. Path 1
    starts where path 0 ends and ends where path 0 starts.
-   A route never has more than 2 paths.
-   Most routes will start with a single path. A second path can be added later for routes
    where the return trip should be illustrated.
-   Paths are drawn independently, so the return path can use different streets. This
    matters because one-way streets often force a different return route.

### Invariants the app enforces

1.  `loop` routes have exactly 1 path, and `waypoints[0]` equals `waypoints[last]`.
2.  `point-to-point` routes have 1 or 2 paths.
3.  If there are 2 paths, `path1.first == path0.last` and `path1.last == path0.first`.
4.  Moving an endpoint in the UI moves it in the other path too. The user does not have to
    keep them in sync by hand.
5.  Intermediate waypoints can differ freely between the two paths.
6.  A user's route numbers are unique, since the number identifies the route and names its
    file.

Data model
----------

A route is stored as a GeoJSON `FeatureCollection` with one `Feature` per path (one or two
features). Each feature has a `LineString` geometry.

``` {.jsonc}
{
  "type": "Feature",
  "id": "uuid",                      // path id
  "geometry": { "type": "LineString", "coordinates": [[lng, lat], ...] },
  "properties": {
    "kind": "loop",                  // "loop" | "point-to-point"
    "direction": 0,                  // 0 = primary (A to B), 1 = return (B to A); always 0 for loops
    "number": "42",                  // string, since routes can be "42X" or "N3"; unique per user
    "name": "Downtown Loop",
    "color": "#e63946",
    "waypoints": [                   // user-placed points the line is built from
      { "id": "uuid", "coordinates": [lng, lat], "name": "optional" }
    ]
  }
}
```

Notes:

-   `waypoints` are the source of truth. `geometry` is derived from them, either as a
    road-snapped path from Valhalla or as straight segments.
-   Endpoints are derived: the first and last waypoint of the path. They are not stored
    separately.
-   `number`, `name`, `color` and `kind` are route-level fields duplicated onto each path
    feature, because GeoJSON has no grouping. The app keeps them in sync when editing.
-   **The route number is the route's identity** within a user's collection. It is used in
    URLs and file names. It must be file-name safe, for example
    `^[A-Za-z0-9][A-Za-z0-9_-]{0,31}$`.
-   Changing a route's number is a rename: the new entry is saved and the old one removed,
    in both `localStorage` and on the server. A rename to a number the user already has is
    rejected with an error.
-   **Automatic numbering:** a new route (and a duplicated route) gets its number
    automatically. The user can change it afterward.
    -   The number is the highest integer route number the user has, plus 1 (or `1` if
        there are none).
    -   If that number is somehow already taken, take the next unused integer instead, and
        keep going until one is free.
    -   "Already taken" is checked against the user's routes in `localStorage` **and** on
        the server. Otherwise the replicating `PUT` could overwrite a server-only route.
-   Ownership comes from where the data is stored (the username in the `localStorage` key
    and server path), not from a property on the feature.

Identity, sessions and storage
------------------------------

### Hardcoded username (temporary)

-   `src/lib/identity.ts` exports the hardcoded `username`. The client needs it for
    `localStorage` keys and URLs.
-   `src/lib/server/identity.ts` exports the same hardcoded `username` for the server only.
-   The session ID is **not** hardcoded. The server generates it (see "Session cookie").
-   The future login plan replaces the hardcoded username.

### Session cookie

-   A session is a logged-in user. The session ID is a ULID.
-   The server (in `hooks.server.ts`) sets a cookie carrying the session ID:
    `Max-Age=2592000` (30 days), `Path=/`, `HttpOnly`, `SameSite=Lax`, and `Secure` in
    production.
-   **Issuing a session:** if a page request has no `sessionId` cookie (first visit, expired
    after 30 days, or cleared), the server generates a new ULID and sets it as the
    `sessionId` cookie. It also creates a **new directory** `data/{username}-{sessionId}/`
    for it, for the hardcoded username.
    - Existing directories and files are never overwritten. If the directory already
      exists (a ULID collision), generate another ULID.
    - Sessions are issued only on page requests, never on `/api` requests. An API request
      without a cookie is refused (see below) and never creates a session.
-   Each session directory contains a `session.json` holding that session's ID, for example
    `{ "sessionId": "01J..." }`. It is written once, when the directory is created, and is
    **never overwritten**.
-   **Every server write** (`PUT` and `DELETE`) must pass this check, with no exceptions:
    the request's `sessionId` cookie must exist, `data/{username}-{sessionId}/` must exist
    for the username in the request path, and the `sessionId` in that directory's
    `session.json` must exactly equal the cookie.
    - A missing or malformed cookie, a missing directory, a missing or unreadable
      `session.json`, or a mismatch is refused with `403` before any file is touched.
    - Validate that the cookie is a well-formed ULID before using it in a path.
    - Compare the two session IDs with a constant-time comparison.
    - The write directory is always derived from the path username and the cookie. It is
      never taken from any other input, so a session can only write inside its own
      directory.
    - The check lives in one shared helper that every write endpoint calls, so a new
      write endpoint cannot skip it.
    - Only the session issuing code in `hooks.server.ts` creates session directories and
      writes `session.json`, never a route endpoint.
-   **Multiple sessions per user:** a new session gets its own directory, so older sessions
    keep working. Their cookies still match their own directories, and nothing a new
    session does touches an older session's files.
-   **Known gap until login exists:** anyone who can reach the server and loads a page
    without a cookie is issued a new session, and a new directory, for the hardcoded
    username. They can only write inside their own directory, but they can create any
    number of directories. Do not expose the server beyond localhost before the login plan
    adds real accounts.

### localStorage (client)

-   One entry per route: `yabus:route:v1:{username}:{routeNumber}`, holding that route's
    `FeatureCollection`. The version segment leaves room for migrations.
-   `localStorage` only ever holds the **current browser user's own routes**.
-   Routes that exist only on the server are never copied into `localStorage`.
-   At 10 to 20 routes per user, the roughly 5 MB limit is not a concern.

### Server filesystem

    data/                                   (git-ignored)
      {username}-{sessionId}/               one directory per session
        session.json                        written once, never overwritten
        {routeNumber}.geojson               one file per route

SvelteKit server endpoints:

-   `GET /api/users/{username}/routes` lists the user's route numbers (and their
    summaries).
-   `GET /api/users/{username}/routes/{routeNumber}` returns a route's GeoJSON. No
    authorization needed, since read-only views are public.
-   `PUT /api/users/{username}/routes/{routeNumber}` creates or replaces a route. Requires
    a valid session for that user.
-   `DELETE /api/users/{username}/routes/{routeNumber}` deletes a route. Requires a valid
    session for that user.

Server rules:

-   Validate `username` and `routeNumber` against strict patterns before using them in
    paths, to prevent path traversal.
-   Session directory names are `{username}-{sessionId}`. Match them against the exact
    pattern `^{username}-[0-9A-HJKMNP-TV-Z]{26}$`, not a loose `{username}-*` glob. A ULID is
    always 26 characters, so this keeps a username like `al` from matching the directories
    of a username like `al-bob`.
-   **Reads for a username:** several session directories can exist for the same username.
    For now that overlap is fine. When finding the routes for a username, use the **first**
    matching directory, meaning the first in sorted order. ULIDs sort by creation time, so
    that is the oldest session's directory. The list endpoint and the single-route endpoint
    both read from that one directory.
-   **Writes** go to the writing session's own directory (see "Session cookie"), which may
    differ from the directory that reads use. As a result, a route written by a newer
    session is not visible to server reads while an older session directory exists for the
    same username. This is accepted for now.
-   Writes are atomic (write to a temp file, then rename).
-   Validate the route invariants server-side before saving.

### Sync rules

1.  **`localStorage` wins.** If a route exists in both places and they differ, the
    `localStorage` version is used and replicated to the server, overwriting it.
2.  **Edits require `localStorage`.** A user edit only succeeds if the route exists in
    `localStorage`. The edit is applied to the `localStorage` copy first, then replicated
    to the server (debounced `PUT`).
3.  **Server-only routes are read-only.** A route that exists on the server but not in
    `localStorage` is displayed read-only. It is never replicated into `localStorage`.
    This includes the current user's own routes if `localStorage` was cleared or they are
    on a different browser.
4.  **Duplicate is the way to get an editable copy.** Duplicating a route (from the
    read-only view) creates a new route in the current user's `localStorage`, which is
    then replicated to the server.
5.  **Delete** removes the `localStorage` entry and sends a `DELETE` to the server. If the
    server `DELETE` fails, that is accepted: there is no retry, and the route may show up
    as a read-only server-only route on a later load.

Views
-----

All three views share the same map component and layer styling. They differ in interaction
and in what data they load.

  -------------------------------------------------------------------------------------------
  View                   Who can use it         What it shows          Interaction
  ---------------------- ---------------------- ---------------------- ----------------------
  **Edit**               Only the creating      One route              Full editing.
                         user, and only for
                         routes in their
                         `localStorage`

  **Read-only route**    Any user               One route              None. A **Duplicate**
                                                                       button creates a new
                                                                       route owned by the
                                                                       current user.

  **Composite**          Any user viewing a     All of one user's      None for now.
                         given user's routes    routes
  -------------------------------------------------------------------------------------------

Proposed URLs:

-   `/u/{username}` is the composite view.
-   `/u/{username}/{routeNumber}` is the read-only route view.
-   `/u/{username}/{routeNumber}/edit` is the edit view. It redirects to the read-only
    view when the route is not editable (not the owner, or not in `localStorage`).

Notes:

-   **Data sources:**
    -   For the current user, the views use `localStorage` first, and fall back to the
        server for routes not in `localStorage` (shown read-only).
    -   For any other user, the views read from the server only.
-   **Composite for the current user:** routes from `localStorage` are shown as editable,
    and server-only routes are shown with a read-only marker.
-   **Ownership check:** the server refuses `PUT` and `DELETE` for anyone without a valid
    session for that username. The client also hides edit controls for non-editable
    routes.
-   **Duplicate:** copies the route's path features with new path and waypoint ids into
    the current user's `localStorage` and replicates it to the server. The copy gets an
    automatically generated number (see "Data model"), so there is no prompt and no
    collision.
-   The edit view is where the Terra Draw interactions are attached. The other two views
    are read-only and never attach it.

Drawing and editing UX
----------------------

Click to add waypoints only. There is no freehand drawing.

-   Click the map to append a waypoint to the active path. After each click the path is
    re-snapped to roads through the `Router`.
-   Drag a waypoint to move it. The affected segments re-snap.
-   Click on the line to insert a waypoint at that position.
-   Select a waypoint and delete it.
-   For a loop, the closing point is the first waypoint. The app adds the matching last
    waypoint automatically.
-   For point-to-point routes, the first and last waypoint are the endpoints. Moving an
    endpoint also moves it on the other path (invariant 4).
-   "Snapping" means snapping the line to roads through Valhalla. Waypoints are also
    snapped to the nearest routable road location by Valhalla.
-   **Adding a return path:** a point-to-point route can get a second path. It starts with
    only the two endpoints, reversed (B then A), and the user adds intermediate waypoints.
    Seeding it with the reversed waypoints of path 0 is deferred (see the last section).
-   A straight-line `Router` is available as a fallback when Valhalla is not running.

Rendering
---------

-   **Basemap:** OpenFreeMap vector tiles. Start with its `liberty` style
    (`https://tiles.openfreemap.org/styles/liberty`), and show the required attribution
    (OpenFreeMap, OpenMapTiles, OpenStreetMap contributors).
-   **Route lines:** `line` layer, `line-color` from `["get", "color"]`.
-   **Route labels:** `symbol` layer with `symbol-placement: "line"` and
    `text-field: ["get", "number"]`.
-   **Direction arrows:** `symbol` layer along each path. Each path has its own arrows, so
    the two paths of a bidirectional route show arrows in both directions where they share
    a street.
-   **Endpoints and waypoints:** `circle` layer for markers (waypoints shown only in the
    edit view).
-   **Overlap within a route:** no offset. The two paths of a bidirectional route, or a
    loop that overlaps itself, are drawn on top of each other and look like a single
    route. Only the arrows indicate direction.
-   **Overlap between different routes:** default rendering (drawn on top of each other).
    A later plan handles it.

Routing (Valhalla)
------------------

-   Use the `/route` endpoint with `"costing": "bus"`. Valhalla respects one-way streets,
    turn restrictions and bus-accessible roads.
-   Send the path's waypoints as `locations`. For a loop, the first and last location are
    the same point.
-   Valhalla returns the shape as an encoded polyline with 6 digits of precision. Decode
    it into the path's `LineString`.
-   Each path is routed on its own. The return path of a bidirectional route is a separate
    request with its own waypoints, so it naturally follows one-way streets in the
    opposite direction.
-   **Location types:**
    -   The first and last locations use `break` (the default). They start and end the
        route.

    -   Intermediate waypoints use `through`. The route must pass through them, without a
        U-turn and without splitting the result into separate legs.

    -   Valhalla's four types differ in two ways: whether a U-turn is allowed at the
        location, and whether it creates a leg boundary.

          Type              U-turn allowed   Creates a leg
          ----------------- ---------------- ---------------
          `break`           yes              yes
          `through`         no               no
          `via`             yes              no
          `break_through`   no               yes

    -   `through` is the default choice for a bus line. Revisit it if it causes failed
        routes or odd detours, for example when a waypoint is placed on a dead-end one-way
        street.
-   The SvelteKit server proxies Valhalla (`/api/valhalla/route`), so the browser does not
    need CORS access to the Docker container.

### Local Docker setup

-   Run Valhalla locally in Docker (for example the `gis-ops/docker-valhalla` image, which
    builds tiles from `.pbf` files in a mounted folder).
-   **Optimized for the target region.** Do not build tiles for the whole US.
    1.  Download the Geofabrik extracts for New Jersey and New York State.
    2.  Clip each to the region polygon with `osmium extract --polygon region.geojson`.
        The polygon is the union of the seven county boundaries, with no extra margin.
        Those counties are the buffer around Hudson County.
        -   Build `region.geojson` with a script in `infra/valhalla/`: download the US
            Census **TIGER/Line** county boundaries, keep the seven counties by FIPS code,
            and dissolve them into one polygon.
        -   Use the full TIGER/Line files, **not** the shoreline-clipped "cartographic
            boundary" files. TIGER/Line counties include the water out to the state line,
            so the polygon stays contiguous across the Hudson and East Rivers.
            Shoreline-clipped polygons would cut off the bridges and tunnels between New
            Jersey and Manhattan, and between Manhattan and the other boroughs, which
            would break routing across them.
        -   `osmium extract` keeps ways that cross the boundary whole by default, so
            streets at the edge are not truncated.
    3.  Merge the clipped files into one `.pbf` and mount it into the container.
-   Check in the scripts and a `docker-compose.yml` for this, but not the data or tiles.
    Keep those in a git-ignored folder.
-   Counties and FIPS codes: Hudson `34017`, Bergen `34003`, Essex `34013` (NJ); New York
    County (Manhattan) `36061`, Kings County (Brooklyn) `36047`, Queens `36081`, Bronx
    `36005` (NY).

### Router interface

``` {.ts}
interface Router {
  route(waypoints: [number, number][]): Promise<[number, number][]>; // snapped path
}
```

The Valhalla implementation sits behind this. A straight-lines implementation is the
fallback.

Milestones
----------

1.  **Scaffold:** SvelteKit + TypeScript managed with Bun and `@risk-tolerance/svelte-adapter-bun`, with
    MapLibre showing the OpenFreeMap basemap centered on Hudson County.
2.  **Identity, session and storage:** hardcoded username, generated ULID session IDs, session cookie,
    per-session directory creation, `localStorage` store, and the server endpoints writing to

    straight-line `Router`, and render it with a color.
4.  **Route metadata:** number, name, color and kind (loop / point-to-point). Automatic

    on rename.
5.  **Labels and arrows:** route number and direction arrows rendered along each path.
6.  **Waypoint editing:** drag, insert and delete waypoints. Enforce loop and endpoint
    invariants.
7.  **Sync rules:** replicate edits to the server, `localStorage` wins, server-only routes
    shown read-only.
8.  **Valhalla:** local Docker setup for the target region, `/api/valhalla/route` proxy,
    and the Valhalla `Router` with `bus` costing.
9.  **Return paths:** add a second path to a point-to-point route, with endpoints locked
    to the first path's.
10. **Read-only route view and Duplicate.**
11. **Composite view** of all of a user's routes.

Deferred to later plans
-----------------------

These were raised during planning but are intentionally not part of this plan.

-   **Login and accounts.** Replace the hardcoded username, and issue the session ID
    on login instead of on the first page visit.
-   **Return-path seeding.** A button on a one-way point-to-point route that creates the
    return path pre-filled with the reversed waypoints of path 0, for the user to adjust.
-   **Overlap between different routes.** Draw routes that share a street side by side
    using MapLibre's `line-offset`.
    -   A constant offset per route is the simple version. Per-section offsets, which
        detect shared stretches of road, are the better version.
    -   `line-offset` is relative to each line's direction, so routes traveling opposite
        ways on the same street flip sides unless compensated.
    -   The offset is in screen pixels, so it needs to scale with zoom.
-   **Route selection / filtering** in the composite view.
-   **GeoJSON import/export.**
-   **Restoring routes from the server into `localStorage`**, for example after clearing
    browser data or on a new browser. For now those routes are read-only and Duplicate is
    the workaround.
-   **Undo/redo and keyboard shortcuts** in the edit view.
